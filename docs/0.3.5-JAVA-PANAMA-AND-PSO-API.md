# XWe 0.3.5 — Java Panama and standard DX12 PSO API

## Java 22+ Foreign Function & Memory API

The Java binding is implemented in `src/xwe/java/api` under package
`xwe.java.api`. It uses the stable C ABI from `include/XWeApplication.h`;
it does not bind C++ classes or use JNI.

Public types:
- `XWeApplicationDesc`: immutable startup configuration.
- `XWeApplication`: owns the native handle and the shared Arena containing
  the UTF-16 window title. The Arena remains alive until native destruction.
- `XWeVersion`: reads the native version string.
- `XWeException`: reports native loading and downcall errors.

The FFM struct layout matches Windows x64:
- `uint32_t struct_size` at byte 0
- 4 bytes of alignment padding
- `const wchar_t* window_title` at byte 8
- width, height and debug flag at bytes 16, 20 and 24
- total size 32 bytes

The binding is Windows x64 only because the native ABI uses 16-bit Windows
`wchar_t` and 64-bit pointers. Set `-Dxwe.library` to the full path of
`xwe_engine.dll` if it is not in the process working directory.

Compile the Java API with JDK 22 or newer:

```powershell
javac --release 22 -d build\java src\xwe\java\api\*.java
```

Example application:

```java
import xwe.java.api.*;

public class Game {
    public static void main(String[] args) {
        var desc = new XWeApplicationDesc("My XWe Game", 1600, 900, true);
        try (var app = XWeApplication.create(desc)) {
            System.out.println("XWe " + XWeVersion.get());
            int exitCode = app.run();
            System.exit(exitCode);
        }
    }
}
```

Run with native access enabled (JDK 22+):

```powershell
java --enable-native-access=ALL-UNNAMED -Dxwe.library="C:\path\to\xwe_engine.dll" -cp build\java Game
```

Call `run()` on the designated main thread. Do not call `close()` while
`run()` is active. Try-with-resources closes the native handle exactly once.

## Standard Direct3D 12 PSO API

Public header: `include/XWe/DX12/PipelineStateCache.hpp`

Namespace: `XWe::DX12`

`PipelineStateCache` now provides:
- `GetOrCreateGraphics`: graphics PSO creation and keyed reuse.
- `GetOrCreateCompute`: compute PSO creation and keyed reuse.
- `GetOrCreateStream`: D3D12 pipeline-state-stream creation through
  `ID3D12Device2`, intended for advanced/mesh pipeline subobjects.
- `Clear`, `Size`, and per-kind counts.

The cache is device-scoped and should be owned by the renderer/device that
creates the PSOs. Stable keys are supplied by the caller and must represent
all state that affects the PSO, including shader bytecode, root signature,
formats, sample configuration, blend, rasterizer and depth/stencil state.
Changing a descriptor without changing its key intentionally reuses the
previous cached PSO. Thread synchronization is the caller's responsibility.

This is the baseline standard API for the planned PSO expansion through
0.4.7. It is not yet a complete pipeline library, disk cache, asynchronous
PSO compiler, shader reflection system, or automatic descriptor hashing.
Those can be added without changing the public call pattern.


## PSO usage example

```cpp
#include "XWe/DX12/PipelineStateCache.hpp"

XWe::DX12::PipelineStateCache psoCache; // one cache per D3D12 device

D3D12_GRAPHICS_PIPELINE_STATE_DESC graphicsDesc{};
graphicsDesc.pRootSignature = rootSignature;
graphicsDesc.VS = {vertexBytecode, vertexBytecodeSize};
graphicsDesc.PS = {pixelBytecode, pixelBytecodeSize};
// Fill blend, rasterizer, depth/stencil, input layout, RTV/DSV formats,
// primitive topology and sample description before creating the PSO.

ID3D12PipelineState* graphics = psoCache.GetOrCreateGraphics(
    device, "aircraft.gbuffer.v1", graphicsDesc);

D3D12_COMPUTE_PIPELINE_STATE_DESC computeDesc{};
computeDesc.pRootSignature = computeRootSignature;
computeDesc.CS = {computeBytecode, computeBytecodeSize};

ID3D12PipelineState* compute = psoCache.GetOrCreateCompute(
    device, "lighting.clustered.v1", computeDesc);
```

The stream overload accepts a fully populated
`D3D12_PIPELINE_STATE_STREAM_DESC` and an `ID3D12Device2`. The cache owns
COM references until `Clear()` or destruction; do not retain raw returned
pointers beyond the cache/device lifetime.

## Namespace and public headers

Engine implementation types now use namespace `XWe`; the DX12 API uses
`XWe::DX12`. Canonical public include paths are under `include/XWe`.
Legacy `include/fx3` paths remain as source-compatibility forwarding headers;
they do not define or expose an `fx3` namespace.

## Build status

The native CMake project is version 0.3.5 and exports `XWeGetVersion()` as
`0.3.5`. Java compilation and the Windows Direct3D 12 build still need to be
run in a Windows/JDK 22 environment before this release can be called tested.
